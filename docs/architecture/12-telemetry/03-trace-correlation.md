This file covers how a Sentry event on the client is correlated to an Axiom trace on the server.

## The bridge

The W3C `traceparent` header is the join key. It is:

1. Generated by a Ferry link on the client for every GraphQL operation.
2. Captured into a request-scoped value on the client at the moment of generation.
3. Sent to the server as the `traceparent` header.
4. Used by the server's Axum middleware as the OTel span parent. See `docs/architecture/04-network-and-graphql/04-trace-propagation.md`.
5. Tagged onto every Sentry event the client emits while the operation is in flight, via Sentry's `scope.setTag('traceId', <hex>)`.

The trace ID is 32 hex characters (16 bytes). The same string lives in Axiom's span store and in Sentry's event tags.

## How to use it

Given a Sentry event:

1. Read the `traceId` tag.
2. Pivot to Axiom and search by trace ID.
3. The trace shows every server-side span that ran for the originating GraphQL operation, including downstream Cypher queries and outbound HTTP calls.

Given an Axiom error trace:

1. Read the trace ID.
2. Pivot to Sentry, filter by the `traceId` tag.
3. Any client-side errors that happened in the same operation surface, with their breadcrumbs and stack traces.

## Server-emitted errors and client-side display

When a GraphQL error response includes `extensions.traceId` (see `docs/architecture/05-server/03-error-handling.md`), the client tags any Sentry event it raises in response with the *server's* trace ID instead of the client-generated one. This handles the case where the server upgraded an incoming request's trace into a fresh one (e.g. because `traceparent` was malformed).

## Limits

Trace correlation does not extend to:

- The REST exception endpoints — they do not carry a client-supplied `traceparent`.
- FCM data messages — they include their originating trace ID in the payload (`traceId` field), but the client does not generate a new trace context for the message itself. Errors processing an FCM message are tagged with the payload's `traceId`.
- Tigris PUT uploads — those are direct from client to Tigris with no Mimir-side observability.
